# Learn from Corrective Feedback

Read the user's examples and referenced files before interpreting the correction. Distinguish an illustration of a broad quality concern from an instruction to fix only that example. Use surrounding conversation and newer decisions to establish the intended scope; do not overfit the latest topic or turn an isolated incident into a universal ban.

Classify missing guidance, weak discovery, conflicting rules, stale source facts or failure to follow existing instructions. Record the durable decision at its owning level through `update-instructions`; do not append the transcript across multiple skills.

State the desired behavior and evidence needed to assess it. For architectural corrections, compare actual upstream responsibilities and specify ownership/lifecycle, not just a class keyword. For cross-platform corrections, define prerequisites and evidence, not a promise that all platforms work. For UI corrections, preserve product intent without freezing every example's pixel values.

Supersede earlier conflicting guidance, preserving non-obvious contracts. Review neighboring instruction concerns when the correction is broad; keep implementation remediation separately scoped. Do not update persistent memory unless explicitly requested. Validate instructions and realistic decisions rather than claiming compliance from new wording alone.
