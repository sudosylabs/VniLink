# Test Infrastructure

Use `unit-tests` for coverage selection and completion, `build-test-infrastructure` for runner/fixture design, and `cross-platform-validation` for environments. A meaningful test asserts externally observable behavior or a contractual invariant, including failure/recovery when relevant.

TypeScript unit tests live beside their module, as in VS Code: `src/<area>/test/<layer>/<name>.test.ts`, where `<layer>` is the environment the subject runs in (`common`, `node`, `browser`, `electron-browser`, `electron-main`, `electron-utility`). They are mocha `suite`s whose first line is `const disposables = ensureNoDisposablesAreLeakedInTestSuite();` (called later, its tracker starts after the suite's own `setup`, so what `setup` creates goes unchecked), add what a test creates to that store, build their subject through `TestInstantiationService`, and run with `node build/run.ts test:unit` (common, node) and `test:unit:electron` (the other layers, in a hidden Electron window). Code under test receives its Electron pieces and collaborators, so no test swaps a module; build tests are in `build/lib/test`; `--run <file>` and `--grep <pattern>` select. A service's test double lives in its own `test/common` folder (`src/platform/engine/test/common/testEngineService.ts`). The other layers here are `test/unit` (the Electron unit runner), `test/native` (built napi module) and `test/smoke` (mocha areas in the running application, with the fixtures its pictures show in `test/smoke/fixtures`) over `test/automation/src` (the launcher, the window driver and a page object per area). Rust services are tested two engines at a time on one computer by `crates/vnilink-testkit` (`node build/run.ts test:service <service>`, `bench:service <service>`); with `--peer` the host half runs in `node build/run.ts testkit:agent` on a second computer. Target reusable drivers and lifecycle fixtures belong in `test/automation`; create that infrastructure only as authorized implementation work. Scenarios use it rather than becoming their own application launchers.

Select areas through a maintained runner interface. A scenario that checks other areas, or a runner edited to select one, is debt, not the template for new tests. Keep test profiles, permissions, temporary files and secret-storage fixtures isolated from the user's development app.
